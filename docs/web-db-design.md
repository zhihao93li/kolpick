# 网页 + 数据库版：需求与设计（草稿）

> **2026-10-26 更新**：数据先原样搬进 Postgres（方案 A，见 [postgres-store.md](postgres-store.md)），决策台和执行器暂留本机；这份文档里的关系表设计和网页部署是第二步。

2026-10-25 起草，同日定了第十二节的 5 件事。飞书多维表格版（kol-ops 0.12.0）的功能已经基本齐全，这份文档写的是替代它的网页 + 数据库版：要做什么、怎么做、先做哪些。仓库怎么管理、怎么切换，已经在 10-24 定了，见文末「开发和切换」。

## 一、为什么换、换掉什么

飞书表这一版能跑，但有几处是表格本身的限制，靠插件里的规则在补：

| 现在的问题 | 原因 | 换成数据库后 |
| --- | --- | --- |
| 「Claude 不能替同事批准」只写在规则里 | 插件用同事本人的飞书授权，能改表就能改「处理」字段 | 批准是网页上的按钮，只有登录的人能点；给 Claude 的接口密钥没有批准权限 |
| 每天的例行要靠一台电脑开着跑 | 收信、催信、发信都走本机 lark-cli 和本人授权 | 服务器定时跑，不依赖谁的电脑 |
| 读表慢、要分页、要缓存「上次读到哪」 | 每次全表读几万行，飞书接口有频率限制 | 直接查询；`cache.ts`、增量读取都不再需要 |
| 选项写错、字段名差一个全角符号就写不进去 | 表格字段按名字匹配 | 表结构由代码管，改结构走迁移脚本 |
| 防重复、额度、发送记录分散在本机和表里 | 发送记录存每台电脑本地 | 发信队列在数据库里，一封信只会有一条记录 |
| 同一个邮箱挂在不同档案下会被重复邀约 | 表格没有唯一约束 | 邮箱唯一 |

**只去掉多维表格。** 飞书企业邮箱（收发信）、飞书群机器人（通知）、飞书账号（登录）都继续用。

## 二、谁用、怎么用

| 角色 | 是谁 | 在新版本里做什么 |
| --- | --- | --- |
| 运营 | 现在一位同事 | 每天看「今日」，处理来信、批准审核项、改跟进状态、录发布内容 |
| 管理员 | 你 | 以上全部，外加批准模板、改设置和发信邮箱、开项目 |
| Claude（插件） | 运营或你在 Claude 里叫它 | 找人、补全档案、给来信分类、写回复草稿、汇总，只能提交到审核队列，不能批准、不能直接发信 |
| 后台定时任务 | 服务器 | 收信、发已批准的信、催信、结案、同步体验码、抓帖子和数据、发群通知 |

### 每天的主流程（和现在一样，只是换了地方）

1. 服务器每 10 分钟收一次信，来信挂到对应的跟进上，标成「待处理」，跟进改成「轮到我们」。现在是每天跑一次 `sync`。
2. 运营或 Claude 处理待处理来信：分成想体验 / 要回复 / 拒绝 / 不用回，要回的写好草稿放进审核队列（现在的 `kol inbox`）。
3. 运营在网页上批准、修改或驳回审核项。
4. 服务器发出已批准的信，执行附带的动作（发体验码、延期、开活动码、结案、永不联系）。
5. 每天上午定时：催信和结案、体验跟进草稿、同步体验码、找新帖、抓数据，把总结发到飞书群，群消息里的链接直接打开对应页面。

### 不常做的流程

- **找人**：在 Claude 里说找什么人、花多少钱，后台跑 Apify，跑完新人进档案，Claude 补全方向、市场、语言、称呼。
- **邀约一批人**：在网页上筛出一批档案，选模板和发信邮箱，提交成一条「决定」审核项，批准后服务器按额度分几天发出。
- **模板**：草稿 → 待审核 → 管理员批准，和现在一样。

## 三、范围

### 第一版要有（能完全替代飞书表）

- 现在插件的所有命令对应的功能：收信、来信处理、审核发信、邀约、催信结案、找人、补全档案、体验码和活动码、体验跟进、找帖子、抓数据、群通知、退信率暂停、MX 检查、新域名预热。
- 页面：见第六节的前 6 个。
- 从飞书表导入全部现有数据，包括往来邮件和操作日志。
- 多项目：主线代码只写通用的找人、联系、跟进、发布、发布效果；TAFU 特有的东西放在 `src/projects/tafu/`，见第五节之后的「通用化：只预留」。

### 第一版不做

- 月度结算：不迁移，以 TAFU 后台为准，见「和 TAFU 运营后台的分工」。
- 分析页：第一版先把分析要用的数据记下来（阶段变化、合作物每日快照），页面放第二批，见「数据分析」。
- 合作进度阶段（#6 跳过的）。
- 小红书、更多找人平台（#12）。
- 手机 App。网页适配手机宽度，够在手机上批准审核项。

## 四、架构

```
            飞书群机器人 ◄── 通知（带页面链接）
                 ▲
浏览器 ──► 网页 + 接口（Node）──► Postgres
                 ▲                   ▲
Claude 插件 ─MCP─┘      后台任务进程 ─┤
                        ├─ IMAP/SMTP ─► 飞书企业邮箱（各发信邮箱）
                        ├─ Apify（找人、帖子、数据）
                        └─ 项目业务接口（TAFU：体验码、活动码）
```

| 部分 | 建议 | 理由 |
| --- | --- | --- |
| 部署 | Zeabur 一个项目三个服务：网页和接口、后台任务进程、Postgres | 和 10-24 定的一致；IMAP 要常驻进程 |
| 语言 | TypeScript，沿用现在的代码 | 分类、催信、发信规则等判断逻辑原样搬过来 |
| 接口 | Hono | 轻，和现有的纯 TS 代码好接 |
| 网页 | React + Vite + shadcn/ui，表格用 TanStack Table | 内部工具，单页应用够用；列表页的筛选和批量编辑是重点 |
| 数据库访问 | Drizzle（表结构写在代码里，自动生成迁移脚本） | 类型直接来自表结构 |
| 任务队列 | pg-boss（用 Postgres 做队列和定时） | 不用再搭 Redis |
| 登录 | 飞书登录（OAuth），只允许本企业的人 | 每个操作都知道是谁做的，批准记录有名字 |
| Claude 接入 | 后台自带 MCP 服务，用接口密钥鉴权 | 插件的技能改成调 MCP，不再调 lark-cli |

### 收发信

- 每个发信邮箱用 IMAP 收信、SMTP 发信，凭据是飞书邮箱的客户端专用密码，加密存在数据库里。
- SMTP 发出后再用 IMAP 把这封信存进「已发送」，同事在飞书邮箱里也能看到。
- 回复带 `In-Reply-To` 和 `References`，邀约和催信不挂到旧邮件串上（现在 0.5.6 的规则）。
- 发信走队列：每封信先写一条记录，再发；SMTP 接受了才算发出，超时算「结果不明」，不自动重发（现在的规则）。
- 每个邮箱的每日上限、预热、退信率暂停线、全公司上限、每分钟上限都在发信前检查。
- 退信从收件箱里识别（现在 `sync` 的做法），把邮箱标成无效。

## 五、数据模型

所有业务表都有 `project_id`，除了 KOL 总库那几张是所有项目共用的。每张表都有 `created_at`、`updated_at`；导入的行带 `feishu_record_id`，方便对账。

### KOL 总库（所有项目共用）

| 表 | 主要字段 | 说明 |
| --- | --- | --- |
| `kols` | 名字、称呼、市场、语言、标签、粉丝数、粉丝分层、简介、备注、`extra`（jsonb，项目自定义字段） | 一个人一行 |
| `kol_accounts` | kol、平台、账号、主页链接、粉丝数 | 平台 + 账号唯一，一个人可以有多个平台 |
| `kol_emails` | kol、邮箱、来源（公开 / 简介 / 隐藏 / 来信）、状态（有效 / 退信 / 无效 / MX 不通） | 邮箱唯一 |

现在「档案」里没邮箱的约 1 万行，进数据库后就是没有 `kol_emails` 的 `kols`。10-24 讨论的「已查无邮箱」轻表是为了少读飞书，数据库里不需要。

### 每个项目自己的

| 表 | 对应飞书表 | 主要字段 |
| --- | --- | --- |
| `project_kols` | 档案里属于项目的部分 | 入库批次、来源任务、`extra`（TAFU 的合作邀约方向、内容类型放这里）、联系许可（可联系 / 永不联系）和原因。永不联系只管这个项目（10-25 定），别的项目照常；跨项目冷却天数照旧生效 |
| `followups` | KOL 跟进 | 阶段（项目阶段，见下文）、`extra`、级别、当前轮到谁、下一步、下次跟进日期、邀约批次、首次邀约 / 最近联系 / 最后来信日期、联系渠道（发信邮箱）、对方要求、约定发布日期、交付清单、结案原因 |
| `offers` | 跟进里的体验码、活动码字段 | 合作物：给 KOL 的东西。类型（由项目模块定义，TAFU 是 `trial`、`partner`）、外部编号（码名）、外部对象编号（TAFU 的合作方编号，用来跳转后台）、`data`（jsonb：上限、已用、到期、折扣、专属连结……）、最近同步时间 |
| `offer_snapshots` | 无 | 合作物每天一行：日期、已用、访客、付款订单、退款订单。接口给的是当前累计数，不存快照就看不出「发布后一周带来几单」 |
| `messages` | 接触记录 | 方向、邮箱、Message-ID（唯一）、邮件串、发件人、主旨、正文、摘要、待处理、时间；`followup_id` 可以为空（陌生发件人） |
| `reviews` | 审核队列 | 类型、跟进、要你定什么、我的判断和建议、收件人、发信邮箱、主旨、草稿、附带动作、状态、提出人、批准人和时间、执行时间和结果 |
| `outbox` | 本机发送记录 + 操作日志里的发信部分 | 审核项或邀约 / 催信、收件人、状态（排队 / 发出 / 结果不明 / 失败 / 退信）、SMTP 回执、尝试时间 |
| `posts` | 发布内容 | 跟进、平台、形式、链接、标题、发布日期、链接已放置 |
| `post_metrics` | 发布内容里的第 1/3/7/30 天字段 | 帖子、第几天、播放、互动、抓取时间（每天一行，不再是 8 个字段） |

`reviews` 的「附带动作」存成一段结构化数据：`{ action: {name, params}, after: {action: "close"|"never", reason} }`。`action.name` 是项目模块提供的合作动作（TAFU 是发码、延期、开活动码），`params` 由那个动作自己校验。现在审核队列里那十几个字段（体验码动作、体验次数、粉丝折扣、发后动作……）都收进这里，网页上按动作显示对应的输入框，输入框由项目模块在代码里定义。

### 配置

| 表 | 对应 | 说明 |
| --- | --- | --- |
| `projects` | 本机 `projects.json` + 「设置」表 | 名称、时区、暂停所有发送、发信规则、催信规则、体验码默认值、活动码规则、发布识别词、找人国家和语言、飞书群机器人 |
| `project_integrations` | 业务数据接口和三个密钥 | 地址、读密钥、体验码写密钥、活动码写密钥，加密存储 |
| `mailboxes` | 发信邮箱 | 地址、渠道名、IMAP/SMTP 凭据（加密）、每日上限、预热、退信率暂停线、启用 |
| `templates` | 模板 | 名称、用途、方向、语言、主旨、正文、状态、审核人和时间 |
| `options` | 批次、标签、渠道等选项 | 项目 + 类别 + 值，网页上随时加 |

### 记录

| 表 | 说明 |
| --- | --- |
| `runs` | 每次定时任务或手动操作：开始、结束、方式、结果、各步数字（现在的运行记录） |
| `stage_changes` | 跟进每次换阶段：从哪个阶段到哪个阶段（项目阶段和系统阶段都记）、时间、谁改的。算「邀约后几天回复」「发码后几成用了」要靠它 |
| `changes` | 谁（人 / Claude / 定时任务）在什么时候把哪一行的哪个字段从什么改成什么。替代操作日志里的「飞书变更」，也补上飞书的「记录历史」 |
| `discovery_jobs` | 找人任务：平台、条件、预算、Apify 运行编号、花费、找到几人 |

## 通用化：只预留（2026-10-25 定）

目标是这套系统能给任何要找 KOL、联系、跟进、发布、看发布效果的项目用。嵌进别的后台以后再说，这一版不考虑。第一版**只在代码里留接口，不做页面上可配置的东西**；扩展点只有 TAFU 一个实现。第二个项目要接时再给它写一套实现，接过两三个、知道哪里真的会变，再考虑做成可配置。

### 现在 TAFU 特有的东西

| 部分 | 现在在哪 | 新版本放哪 |
| --- | --- | --- |
| 体验码：发码、延期、用量同步、体验跟进提醒、来信分类里的「想体验」 | `trial.ts`、`trialfollow.ts`、`codes.ts`、`inbox.ts` | TAFU 模块的合作动作和提醒规则 |
| 活动码：专属连结、账本连结、粉丝折扣、阶梯分润、市场对应 | `partner.ts` | TAFU 模块的合作动作 |
| 阶段「体验中」「已看报告」 | 写在主线代码里 | TAFU 模块的阶段配置 |
| 月度结算 | 「月度结算」表 | 不迁移；结算、分润、付款都以 TAFU 后台为准 |
| 档案字段「合作邀约方向」「内容类型」，找人后补全的那 5 个字段 | `classify.ts`、`data.ts` | TAFU 模块定义的自定义字段，存在 `extra` |
| 默认时区 `+08:00`、找人默认 `TW`/`zh`、繁体占位符 | `base.ts`、`discovery/run.ts`、模板 | 项目设置；主线没有默认国家和语言 |

### 预留的扩展点

| 扩展点 | 主线代码 | TAFU 模块 |
| --- | --- | --- |
| 阶段 | 只认识系统阶段：已邀约、已回复、合作中、已约发布、已发布、结案。催信、找帖子、今日清单只看系统阶段 | 自己的阶段挂到系统阶段下，例如体验中、已看报告 → 合作中 |
| 自定义字段 | 档案、项目档案、跟进各有一个 `extra`（jsonb）；网页按字段定义显示和编辑 | 在代码里定义字段名、类型、选项、找人后要不要让 Claude 补全 |
| 合作动作 | 一个接口：名称、参数和校验、执行（调外部系统）、执行结果写进 `offers` 和模板占位符 | 发码、延期、开活动码，调 TAFU 的 `kol-data` 接口 |
| 合作物状态和提醒 | 定时同步 `offers` 的状态；提醒规则是一个接口，产出审核项 | 体验码用量同步、未用 / 停滞 / 到期三条提醒 |
| 登录、通知 | 各一个模块，主线只调模块 | 都是飞书 |

项目用哪个模块，写在 `projects` 表里（例如 `module: "tafu"`）；没有模块的项目只有通用流程，没有合作动作。项目模块还可以提供「去业务后台看这个合作」的链接（TAFU 是 `/admin/kol/<合作方编号>`），后台地址写在模块配置里。

### 明确不做

页面上的阶段 / 字段 / 动作配置器、通用的外部动作约定（按配置生成表单）、自助注册租户、计费、界面多语言、嵌入别的后台。界面文字统一放在一个文件里。

## 和 TAFU 运营后台的分工（2026-10-25 定）

TAFU 后台（tafu-nodejs 的 `/admin`）管订单与交付、退款、平台券码，以及 KOL 合作里的活动链接、粉丝优惠、阶梯分润、KOL 账本、月度封账和结算。按它的规则，后台不扩成通用管理平台，对插件只开 `/api/kol-data` 这一个窄接口。

**跟人打交道的部分在 kolpick，跟钱有关的部分在 TAFU 后台**，两边只通过 `kol-data` 接口打交道。

| 环节 | 归谁 | 说明 |
| --- | --- | --- |
| 找人、邀约、来信、审核、跟进阶段 | kolpick | |
| 发体验码、延期、开活动码 | kolpick 发起，TAFU 执行 | 运营在 kolpick 批准，TAFU 模块调接口建码；码和活动本身存在 TAFU |
| 码的用量、活动的访客、付款订单、退款订单 | TAFU 为准，kolpick 每天同步 | 用于体验跟进提醒和分析；只同步数字，不同步金额 |
| 找帖子、抓播放和互动 | kolpick | |
| 分润规则、账本、结算、付款、退款 | 只在 TAFU | kolpick 不存、不算 |
| 改活动规则、停用、重置账本 | 只在 TAFU 后台手动做 | 接口本来就不允许 |

- 开活动码时把 TAFU 返回的合作方编号存进 `offers`，KOL 详情页放「在 TAFU 后台查看」，跳到 `/admin/kol/<编号>` 看账本和结算。要确认开活动码接口（tafu-nodejs PR #29）会返回合作方编号，不返回就请 TAFU 加上。
- KOL 详情页显示的合作效果只有接口给的数字（已用、访客、付款订单、退款订单），不显示金额。
- 不做：两边页面互相嵌入、kolpick 直接读 TAFU 数据库、统一登录、把 KOL 联系方式或跟进进度传给 TAFU。

## 数据分析（2026-10-25 定）

TAFU 的数字每天同步进 kolpick 的库，靠码名对到跟进上，所以分析在 kolpick 里做，不用两边的数据库直连。这改掉了 10-25 早些时候「漏斗报表归 TAFU 业务端」的判断：那时插件没有地方存和展示，现在漏斗的大部分数据都在 kolpick。

转化漏斗每一步的来源：

| 步骤 | 来源 |
| --- | --- |
| 入库 → 有邮箱 → 邀约 → 回复 | kolpick |
| 想体验 → 发体验码 → 开活动码 | kolpick（审核和合作动作） |
| 体验码用过几次 | TAFU，每日同步 |
| 发布 → 播放、互动 | kolpick（找帖子、抓数据） |
| 活动访客 → 付款订单 → 退款 | TAFU，每日同步 |
| 金额、分润 | 只在 TAFU 后台 |

## 十一、开发和切换

**目标：开发网页版的整个过程中，同事用的飞书版不受影响。** 仓库按 10-24 定的方式管理（业界叫法：主干开发、抽象分支、功能开关、绞杀者模式、稳定发布通道）。

### 两条线

- **main**：所有开发都在这里，飞书版和网页版都是。`npm test`、`npm run typecheck` 不过不推。
- **stable**：只给同事安装插件用（`/plugin marketplace add zhihao93li/kolpick#stable`）。只往前快进，从不在上面直接改代码。

不给网页版开长期分支：飞书版这段时间还会继续修，两条线共用判断逻辑，分开久了合并会大面积冲突。

### 保护飞书版的规则

1. **同事只装 stable。** main 上推了什么，同事都拿不到，直到你把 stable 推过去。
2. **网页版只放新目录**（见下面的目录表），插件打包不会引用它们；`bundle.test.ts` 检查打包结果。网页版的依赖（Postgres、Hono、React 等）写在 `apps/*` 自己的 `package.json` 里（npm workspaces），不加进根目录，免得影响插件的 `npm ci` 和打包。
3. **共用代码改动走短分支**（`src/kolops/` 里两边都用的判断逻辑，最大的一次是第 1 阶段抽 `Store`）：飞书版行为不变，现有测试全过、试用副本上全流程跑通，单独发一个飞书版版本，同事用几天没问题再继续。
4. **飞书版插件的技能不改。** 网页版的插件另做一个 `kol-ops-web`，放在同一个插件市场里，只有测试的人装；切换前同事的插件一个字都不变。切换时再让同事卸旧装新。
5. **按项目切换。** `~/.kol-ops/projects.json` 里每个项目写 `"store": "feishu" | "api"`，不写就是飞书。网页版后台的定时任务只处理 `api` 项目。
6. **同一个项目任何时候只能有一边在发信和收件同步**，否则会重复发信。开发期间网页版只接测试项目和测试邮箱，不碰 hello@、mei@ 和正在用的飞书表。

### 日常三种改动

**A. 飞书版修问题、加功能（同事会用到）**

1. 在 main 上改，`plugins/kol-ops/.claude-plugin/plugin.json` 版本号加一，`npm run build:plugin`，提交。
2. 用自己电脑上的插件在试用副本上跑相关操作。
3. 没问题就发布：

```bash
git switch stable && git merge --ff-only main && git push origin stable && git switch main
```

```bash
git tag kol-ops-v0.12.1 stable && git push origin kol-ops-v0.12.1
```

4. 告诉同事运行 `/plugin marketplace update kolpick`，然后新开一个会话。

main 上有还没验证完的改动、又要急修线上时，只把那个修复挑到 stable：

```bash
git switch stable && git cherry-pick <修复的提交号> && git push origin stable && git switch main
```

**B. 做网页版（同事感知不到）**：只改新目录，随时提交到 main。开发期间 Zeabur 从 main 部署，只接测试项目。

**C. 改共用代码**：按上面第 3 条。
